## 0. 이 문서의 위치

`README.md`는 **무엇을 만들었고 어떻게 검증해 왔는가**(검증 과정 1~12번)를 기록한다.
이 문서는 **앞으로 무엇을 목표로 하고, 무엇을 근거로 판단하는가**를 다룬다. 구체적으로:

- 프로젝트 목표의 재정의와 그 근거 (1·2장)
- 사실 태그의 정의 — **정본은 이 문서 4장**이다. 코드(`TagService`, `evaluate_tags.py`)가 여기와 다르면 코드가 틀린 것
- 태그를 "검증됐다"고 부를 기준 — **실전 기록이 쌓이기 전에 고정**한다 (5장)
- 결정 기록(7장)과 리스크(8장)

**설계와 구현 현황을 구분한다.** 본문은 목표 구조를 적고, 코드가 아직 다른 곳은
`> **구현 현황 (날짜)**` 박스로만 적는다.

### 확정된 프로젝트 정의 (2026-09-30 기준)

| 항목 | 확정 내용 |
|------|-----------|
| **대상** | KOSPI+KOSDAQ 시가총액 상위 100 (최근 수집 기준). 순위에서 밀린 종목은 분석하지 않는다 |
| **촉이 답하는 질문** | 1순위 **"오늘 뭘 봐야 하지?"**(B, 스크리너) · 2순위 **"이 신호에 진짜 엣지가 있나?"**(C, 검증) · 마지막 **"어떤 종목이 시장보다 나을까?"**(A, 예측) |
| **순서** | B·C를 먼저 발전시키고, C를 통과한 신호만 A의 재료로 쓴다 (D1) |
| **화면이 주장하는 것** | 사실(태그·점수·뉴스)만. 예측력이 검증되지 않은 확률은 보여주지 않는다 (D2) |
| **성과의 정의** | 태그 종목의 h영업일 뒤 수익률 − 그날 분석 종목 전체의 **평균** (시장 대비, 5.2) |
| **최종 판정 근거** | 태그를 정한 날 **이후**에 쌓인 실전 기록. 과거 백테스트는 1차 필터일 뿐이다 |
| **가격 기준** | KRX 확정 종가(15:30). 장중 가격·NXT 시간외 체결가는 쓰지 않는다 (D6) |
| **철회된 항목** | 화면의 상승확률·하락확률·유력 구간(D2), 실전 성과 신규 편입(D8, 2026-09-29) |

### 세 가지 목표의 관계

| | B. 스크리너 | C. 검증 플랫폼 | A. 예측기 |
|---|---|---|---|
| 질문 | 오늘 뭘 봐야 하지? | 이 신호에 엣지가 있나? | 무엇이 시장보다 나을까? |
| 산출물 | 사실 태그, 점수, 뉴스 재료성 | 태그별 실전/백테스트 성과표 | 통과 태그 조합 확률(보정됨) |
| 성공 기준 | 판단 시간을 줄여주는가 | 정직하고 재현 가능한가 | 비용 차감 후 초과수익, 확률 보정 |
| 선행 조건 | 없음 | B가 기록을 남겨야 함 | C 통과 신호가 있어야 함 |
| 현재 | **B1 구현** | **C1 구현, 실전 기록 시작** | 대기 |

**B만으로도 쓸모가 있어야 한다.** A가 끝내 나오지 않아도 B·C는 그 자체로 가치가 있게 설계한다.

## 1. 설계 원칙

| # | 원칙 | 구체적 의미 |
|---|------|-------------|
| P1 | **화면은 검증된 만큼만 주장한다** | 예측처럼 읽히는 값은 C를 통과해야 화면에 나온다. 통과 전에는 사실로만 표시한다 |
| P2 | **판정 기준은 결과를 보기 전에 고정** | 태그 정의(4장)와 판정 기준(5장)은 실전 기록 시작 전에 적는다. 바꾸면 버전을 올리고 이전 기록과 섞지 않는다 |
| P3 | **실전 기록이 최종 판정** | 같은 과거 데이터에 후보를 여럿 시험하면 우연한 통과가 섞인다(다중비교). 백테스트는 거르기만 한다 |
| P4 | **겹치는 관측을 따로 세지 않는다** | h일 성과는 매일 기록해도 h일씩 겹친다. 판정은 h영업일 간격의 겹치지 않는 창으로만 센다 |
| P5 | **B에 넣을 때 C로 검증 가능한지 함께 정한다** | 과거 시점으로 계산 가능한 태그는 백테스트+실전, 불가능한 것(뉴스)은 실전만. 검증 불가능한 정보는 A의 재료가 될 수 없다 |
| P6 | **정의는 한 곳에** | 태그 규칙의 정본은 이 문서 4장, 코드 정본은 `TagService.compute`. 파이썬 재현(`evaluate_tags.tags_for_day`)은 같은 규칙을 따르고 자가점검으로 묶는다 |
| P7 | **확정된 가격만 쓴다** | 분석·진입가·성과는 KRX 확정 종가 기준. 장중에 수집하면 오늘 행은 저장하지 않는다 |

## 2. 방향 전환의 근거 (2026-09-30 점검)

코드와 모델 파일을 직접 확인한 결과, **화면이 약속하는 것과 검증된 것 사이에 차이**가 있었다.

| # | 발견 | 근거 |
|---|------|------|
| F1 | 화면의 "상승확률(학습 기반, 50영업일 기준)"은 사실상 무작위 | 배포 모델 `rise_model.json` holdout AUC **0.5016** |
| F2 | README의 "검증을 통과할 때만 모델 사용"이 코드에 없음 | `train_model.train_and_save_horizon`은 AUC와 무관하게 저장, `RiseProbabilityService.predict`는 파일만 있으면 사용 |
| F3 | "상승확률" 이름이 라벨과 다름 | 라벨은 `relative`("그날 중앙값보다 잘했나")인데 화면은 상승/하락(보합포함)으로 표시 — 하락장에서도 60%가 나올 수 있음 |
| F4 | 실전 검증이 멈춰 있음 | 2026-09-29 실전 성과 신규 편입 중단 이후 앞으로의 기록을 쌓는 장치가 없음 |
| F5 | 기술 지표 8개에는 신호가 없음 | 생존편향 제거(PIT) 후 50일 AUC 0.498~0.502, 트리 모델도 동일 (README 8·12번) |
| F6 | 가장 일관된 신호는 순발행, 그러나 약함 | 50일 IC 0.052, 단독 순위 IC −0.090(10개 폴드 모두 음) — 거래비용 차감은 아직 계산한 적 없음 |

F1~F4는 신뢰 문제이고, F5·F6은 "예측기(A)부터 만들면 막힌다"는 뜻이다.
그래서 **B(사실을 정직하게 보여주기)와 C(무엇이 통하는지 계속 재기)를 먼저** 세우고,
C를 통과한 것만 A로 올린다.

### B1 — 화면 정리 (구현됨)

- 대시보드 "상승확률" 열 → **태그** 열. 종목 상세 "상승 확률" 카드 → **태그** 카드
- 하락확률·유력 구간·유력 하락구간 표시 제거, 추이 차트는 종합점수만
- 실전 성과 표에서 상승확률 열 제거, 점수 열은 "선정일 ○○점수"로 명시
- 챗봇·AI 리포트 프롬프트에서 상승확률 설명 제거 → 태그는 사실이며 신호가 아니라고 설명
- 상승확률은 계속 **계산·저장**한다(`recommendations.rise_probability`). 화면에만 안 보인다 — A 단계에서 비교 기준이 된다

### C1 — 태그 추적 (구현됨)

- 분석이 끝날 때마다 `TagService.snapshot(오늘)`이 그날 태그를 `tag_snapshots`에 통째로 다시 쓴다(같은 날 재분석 대비)
- 태그 입력값(`vol60`, `issuance_252`, `material_news_score`, `momentum_12m`)은 `recommendations`에 그날 값으로 남는다 — 정의를 바꿔도 과거를 다시 계산할 수 있다
- `python-collector/evaluate_tags.py`가 백테스트(marcap PIT)와 실전(`tag_snapshots`)을 나란히 집계하고 5장 기준으로 판정한다

## 4. 사실 태그 v1 (정본)

태그는 **"지금 이 종목이 이런 상태다"**라는 사실이다. 매수·매도 신호가 아니며, 화면에서도
방향을 암시하는 색을 쓰지 않는다(D3). 순위형 태그의 경계는 **필터 전, 그날 분석 종목 전체**로 잡는다.

| 태그 | 화면 표시 | 정의 | 입력 · 계산 위치 | 백테스트 | 사전 가설 |
|------|-----------|------|------------------|----------|-----------|
| `MOMENTUM_TOP20` | 모멘텀 상위 20% | 12-1개월 모멘텀(252→21영업일 전 수익률)이 그날 상위 20% | `momentum_12m` · `TechnicalAnalysisService.momentum12m` | 가능 | + |
| `LOW_VOL20` | 저변동성 | 60영업일 일간수익률 표본표준편차가 그날 하위 20% | `vol60` · `TechnicalAnalysisService.volatility60` | 가능 | + |
| `ISSUANCE_UP` | 주식수 증가 | 순발행 log(N_t / N_t−252) ≥ +0.02 | `issuance_252` · `collect.compute_issuance` | 가능 | − |
| `BUYBACK` | 주식수 감소 | 순발행 ≤ −0.02 | 〃 | 가능 | + |
| `NEWS_POS` | 재료성 호재 | 최근 lookback(3일) 뉴스 중 \|감성점수\| 최대값이 ≥ +0.8 | `material_news_score` · `RecommendationService.strongestRecentNewsScore` | **불가** (과거 뉴스 소급 불가) | + |
| `NEWS_NEG` | 재료성 악재 | 위 값이 ≤ −0.8 | 〃 | **불가** | − |

정의 세부:

- **순위 경계**: 값이 있는 종목 n개 중 `ceil(n × 0.2)`번째 값 이상(저변동성은 부호를 뒤집어 같은 방식). `TagService.topShareCutoff`
- **순발행 N**: 시가총액 / 수정종가지수(KRX 등락률 누적곱). 상장주식수를 그대로 쓰면 액면분할 때 수십 배로 튄다 —
  2021~2026 분할급 변화 140건에서 N의 변화 중앙값 2%로 연속성 확인. 합병·재상장 일부는 여전히 튄다(R6)
- **순발행 경계를 절대값(±2%)으로 둔 이유(D4)**: 현재 상위 100 기준 중앙값이 약 0(75% 분위 +0.03%)이라, "상위 20%"로 자르면
  +0.3% 같은 잡음이 "주식수 증가"로 표시된다
- **재료성 경계 0.8(D13)**: 처음엔 감성 프롬프트의 "|0.6| 이상 = 구체적·즉각적 재무 임팩트" 기준을 그대로 썼지만, 첫 기록(2026-09-30)에서
  100종목 중 호재 56·악재 22개가 걸려 구분력이 없었다. 최근 3일 뉴스 여러 건의 최대값을 쓰므로 개별 기준보다 자주 걸린다.
  실측 분포: 경계 0.7 → 32/10, **0.8 → 8/2**, 0.9 → 0/0. 0.8은 개별 뉴스 1,718건 중 상위 0.6%. 순위형(상위 10%)은 재료 뉴스가 없는 날에도
  억지로 태그가 붙어 "재료성"의 뜻과 맞지 않아 택하지 않았다
- **사전 가설 근거**: 모멘텀·저변동성·순발행은 문헌상 반복 보고된 효과. 순발행은 이 프로젝트의 PIT 실험에서도 10개 폴드 모두 음(README 14번)

> **구현 현황 (2026-09-30)** — `tag_snapshots`와 `recommendations`의 새 열은 Spring 재시작 시 `ddl-auto=update`로 생긴다.
> `stocks.issuance_252`는 재시작 **후** 첫 수집부터 채워진다(열이 없으면 수집기는 경고만 남기고 넘어간다).
> 기존 날짜의 추천 행에는 태그 입력값이 없으므로, **태그는 배포 후 첫 분석부터** 표시·기록된다.

## 5. C1 판정 기준 v1 (2026-09-30 고정)

**실전 기록이 시작되기 전에 고정한다.** 이 기준을 바꾸려면 v2로 올리고, v1 기록으로 v2를 판정하지 않는다.

### 5.1 통과 조건 (기간 h = 5, 20, 50영업일 각각)

모두 만족해야 "통과":

1. **겹치지 않는 창 ≥ 6개** — 기록된 날짜 중 직전에 뽑은 날보다 h거래일 이상 뒤인 날만 순서대로 센다
2. **방향** — 창 평균 초과수익의 부호가 4장의 사전 가설과 같다. 반대면 크기와 무관하게 불통과
3. **크기** — |창 평균 초과수익| ≥ **0.5%**(5일) / **1.0%**(20일) / **2.0%**(50일). 왕복 거래비용(약 0.3%)보다 확실히 위
4. **일관성** — 가설 방향과 같은 부호인 창이 **70% 이상**

"창 부족"은 불통과가 아니라 **아직 판정 불가**다.

### 5.2 성과 계산

- 초과수익 = 태그 종목의 h영업일 뒤 수익률 − **그날 분석 종목 전체의 평균** 수익률
- **평균인 이유(D5)**: 수익률은 오른쪽 꼬리가 길어 "수익률 − 중앙값"의 평균은 어떤 종목 묶음이든 양수가 된다.
  첫 백테스트에서 가설이 반대인 태그(주식수 증가)까지 전부 +0.4~3.6%로 나와 바로잡았다 — 보조지표 실험(README 13번)과 같은 함정
- 모든 날짜 평균(`allDatesMean`)은 참고용으로만 같이 적는다(겹침 때문에 판정에 쓰지 않음)

### 5.3 실전 판정이 가능해지는 시점 (추정)

첫 기록이 2026-10-01 분석이라고 가정하면, 6번째 창의 성과까지 확정되려면 거래일로 대략 6h일이 필요하다.

| 기간 | 필요 거래일 | 대략적 시점 |
|------|-------------|-------------|
| 5일 | ~30 | 2026-11 중순 |
| 20일 | ~120 | 2027-03 말 |
| 50일 | ~300 | 2027-12 |

50일 판정은 1년 이상 걸린다(R2). 실제 운영에서는 5일·20일 결과로 먼저 방향을 잡는다.

### 5.4 백테스트 기준선 (2026-09-30, marcap PIT 2021-01 ~ 2026-09)

`python evaluate_tags.py` 결과. **v1 태그 중 백테스트를 통과한 것은 없다.**

| 태그 | 5일 창 평균 (가설 방향/창) | 20일 창 평균 (가설 방향/창) | 50일 창 평균 (가설 방향/창) | 50일 전체일 평균 |
|------|---------------------------|-----------------------------|-----------------------------|------------------|
| MOMENTUM_TOP20 (+) | +0.29% (130/230) | **+1.12%** (32/57) | **+3.36%** (15/23) | +2.71% |
| LOW_VOL20 (+) | +0.00% (144/268) | +0.06% (32/67) | +0.17% (15/26) | −0.05% |
| ISSUANCE_UP (−) | +0.02% (122/230) | −0.20% (33/57) | +0.83% (13/23) | −0.08% |
| BUYBACK (+) | +0.08% (110/230) | +0.11% (24/57) | +0.55% (12/23) | +1.36% |

해석:

- **모멘텀**은 크기는 기준을 넘지만(20일 +1.12%, 50일 +3.36%) 일관성이 56~65%로 70%에 못 미친다 — 강하지만 구간별로 흔들린다(README 11번과 같은 결론)
- **저변동성**은 초과수익이 거의 0이다. 모델 실험에서 IC가 +0.097이었던 것은 "중앙값을 넘을 확률"이 높다는 뜻이지 평균 수익이 높다는 뜻이 아니다 — 두 지표의 차이가 그대로 드러남
- **순발행**은 순위 전체로 보면 가장 일관된 신호였지만(IC −0.090, 10/10), ±2% 경계로 자른 태그로는 드러나지 않는다. 효과가 극단값보다 순위 전반에 퍼져 있다는 뜻 — 태그보다 연속값(순위) 표시가 맞을 수 있다(9장 Q2)
- 이 결과는 **태그를 내릴 이유가 아니다.** 태그는 사실 표시이고, 백테스트는 다중비교에 취약한 1차 필터다. 실전 기록이 최종 판정한다(P3)

## 6. 데이터 흐름과 구현

```
[collect.py]  (서버 시작 보정 · 6시간 스케줄 · 수동 버튼)
   ├─ 시총 상위 100 → stocks (base_date = 오늘)
   ├─ 5년 일봉 → price_history      ※ 16:00 KST 전이면 오늘 행 제외 (confirmed_until, D6)
   └─ marcap(올해+작년) → 순발행 → stocks.issuance_252

[RecommendationService.runFullAnalysis]  (최근 수집 기준 상위 100만)
   └─ 종목별: 기술지표 · 뉴스 감성 · 점수 · 태그 입력값(momentum_12m, vol60, issuance_252, material_news_score)
        → recommendations (rec_date = 오늘)
   └─ 전 종목 끝나면 TagService.snapshot(오늘) → tag_snapshots (tag_version = v1)

[화면]
   ├─ /api/recommendations → 추천 + 그날 태그 (분석 도중엔 직전 완료 날짜)
   └─ /api/stocks/{ticker}/tags → 최신 스냅샷의 태그

[evaluate_tags.py]  (수동 실행)
   ├─ backtest: marcap PIT에서 같은 규칙으로 태그 재계산 → 초과수익
   └─ live: tag_snapshots + recommendations(그날 유니버스) + price_history → 초과수익
   → 5장 기준 판정 → model/tag_evaluation_result.json
```

| 파일 | 역할 |
|------|------|
| `service/TagService.java` | 태그 규칙(정본), 스냅샷 저장, 조회 |
| `domain/TagSnapshot.java` | `tag_snapshots` (snap_date, ticker, tag, tag_version), (날짜·종목·태그) 유니크 |
| `service/TechnicalAnalysisService.java` | `momentum12m`, `volatility60` |
| `service/RecommendationService.java` | 태그 입력값 저장, 분석 끝에 스냅샷 |
| `static/js/tags.js` | 태그 라벨·정의(툴팁)·근거, 화면 하단 "지표·태그 설명" — 대시보드·상세 공용 |
| `python-collector/collect.py` | `confirmed_until`, `compute_issuance`, `update_issuance` |
| `python-collector/evaluate_tags.py` | 태그 성과 집계·판정 |
| `python-collector/test_collect.py`, `test_evaluate_tags.py` | 자가점검 (`python test_*.py`) |

| 태그 성과 집계 (백테스트+실전) | `cd python-collector && DB_USER=... DB_PASSWORD=... python evaluate_tags.py` |
